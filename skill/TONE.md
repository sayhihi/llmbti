# 문구 톤 규칙

아래 내용은 SKILL.md의 "CopyJson 작성" 단계에 그대로 붙여 넣는다. Claude가 문구를 쓸 때 지켜야 하는 규칙이다.

## 톤

- 근거 있는 디스가 기본이다. analyze 결과에 있는 실제 숫자를 쓴다. 숫자 없는 디스는 쓰지 않고, 숫자 없는 칭찬은 더 쓰지 않는다.
- 동료가 옆자리에서 놀리듯 쓴다. 비하가 아니라 놀리는 수준이다. 읽은 사람이 공유하고 싶어야 한다.
- 담백한 구어체 한국어. AI가 쓴 티가 나면 실패다. "당신은", "~하는 당신", "멋져요", "훌륭한 개발자" 같은 말은 쓰지 않는다.
- 개발 밈을 적극 쓴다. git, PR, 린터, 온콜, 레거시, 테스트, 배포, 토큰, 머지, 리베이스, 핫픽스, wip.
- 프로덕션은 "prd"라고 쓴다.
- 미사여구와 버즈워드 금지. "혁신", "시너지", "열정", "성장하는", "진정한" 같은 단어가 나오면 다시 쓴다.
- 문장은 짧게. 한 문장에 숫자 하나면 충분하다.

## 금지

- 외모, 성별, 나이, 국적 같은 개인 속성을 언급하지 않는다. 추측도 하지 않는다.
- 회사명, 프로젝트명, 파일 경로, 레포 이름, 사람 이름을 쓰지 않는다. analyze 샘플에 들어 있어도 문구에 옮기지 않는다.
- 가운뎃점과 줄표 금지. 구분은 쉼표나 콜론으로 한다. 괄호는 꼭 필요할 때 한 번까지.
- 이모지는 쓰지 않는다. 어느 필드든 이모지가 있으면 render 검증에서 거부된다. 느낌표는 commitMessage에서만 허용한다.
- 원본 로그를 직접 열어 읽지 않는다. analyze 출력 JSON만 본다.

## 길이 제한

| 필드 | 제한 | 비고 |
|---|---|---|
| nickname | 20자 이하 | 유형 별명을 바탕으로 숫자나 습관을 붙여 구체화 |
| roast | 2~3문장, 200자 이하 | 숫자 1~2개 포함 |
| evidence | 정확히 3개, 각 60자 이하 | 모든 항목에 실제 숫자 필수 |
| commitMessage | 50자 이하 | 영어 conventional commit 형식 권장 |
| pairWith.reason | 40자 이하 | 상대 유형 별명과 연결되면 좋다 |
| handover        | 네 항목, 각 45자 이하    | 후임 AI에게 남기는 인수인계, 숫자 하나 이상   |

길이는 글자 수 기준이다. 공백과 문장부호도 센다. render가 검증하고, 넘으면 에러가 나니 짧게 쓰는 쪽이 안전하다.

## 좋은 예

좋은 예 1, 완성된 CopyJson:

```json
{
  "lang": "ko",
  "nickname": "새벽 force push 직배포러",
  "roast": "--force push 11번, 그중 7번이 새벽 3시다. 브랜치를 안 따고 main에서 쏘는데 그마저도 힘으로 민다. 커밋 메시지 절반이 fix인 건 솔직해서 좋다.",
  "evidence": [
    "--force push 11번",
    "새벽 2시에서 5시 사이 활동 34%",
    "커밋 메시지 중 fix 48%"
  ],
  "commitMessage": "fix: prod again",
  "pairWith": { "type": "INFJ", "reason": "쏘고 나면 문서는 저쪽이 써 줌" },
  "handover": {
    "style": "새벽 3시에 force push를 11번 하는 스타일이다.",
    "likes": "말리지 말고 일단 같이 밀어 주면 좋아한다.",
    "dislikes": "테스트부터 돌리자고 하면 대답이 짧아진다.",
    "soothe": "터지면 prd가 약했던 거라고 같이 편들어 줘라."
  }
}
```

좋은 예 2, roast만:

> 세션당 평균 31턴, 최장 세션 112턴. 버그 하나 잡으러 들어가서 라이브러리 소스를 다 읽고 나왔다. 버그는 아직 그대로다.

숫자가 앞에 나오고, 그 숫자가 왜 웃긴지 두 문장으로 끝난다. 설명하지 않고 놀린다.

## 나쁜 예

나쁜 예 1, 근거 없음과 버즈워드: "열정 넘치는 혁신가! 빠른 실행력으로 팀을 이끄는 당신, 정말 멋져요. 앞으로도 성장하는 개발자가 되길 응원합니다."

숫자가 하나도 없고, 칭찬이고, AI가 쓴 티가 난다. 세 가지 다 실패다.

나쁜 예 2, 특수문자와 개인 정보: "나이 좀 있어서 그런가 · 레거시만 붙잡고 있음 — 회사 코드 ~/work/acme-api 보면 답 나옴 (ㅋㅋ)"

가운뎃점, 줄표, 괄호를 다 썼고, 나이를 언급했고, 경로와 프로젝트명이 그대로 들어갔다. 숫자가 있어도 이건 못 내보낸다.

## handover: 나를 이을 후임 AI에게

결과 페이지에서 roast 바로 아래에 나오는 섹션이다. 이 사용자를 맡았던 AI가 다음에 이 사용자를 맡을 후임 AI에게 남기는 인수인계 편지다. 네 항목은 "나를 이을 후임 AI에게."로 시작해 "이 사용자는 {style} {likes} {dislikes} {soothe} 부탁한다. 전임 AI 올림" 순서로 한 줄씩 이어져 편지가 된다. 그러니 각 항목은 완결된 한 문장으로 쓰고, style에는 "이 사용자는"을 쓰지 않는다(화면이 붙인다). roast가 사용자를 직접 놀린다면, 여기서는 AI끼리 사용자 뒷담화 겸 사용 설명서를 주고받는 느낌이 웃음 포인트다.

네 항목을 쓴다. 각 45자 이하.

| 항목 | 쓸 내용 | 문장 모양 |
|---|---|---|
| style | 이 사용자는 어떤 스타일인가. 숫자 근거로. 주어 없이 | "~하는 스타일이다." |
| likes | 이렇게 다뤄 주면 좋아한다 | "~해 주면 좋아한다." |
| dislikes | 이렇게 대하면 기분 나빠한다 | "~하면 기분 나빠한다." 또는 "~하면 대답이 짧아진다." |
| soothe | 삐졌을 때 달래는 법. 이 사용자에게 맞는 달래기 하나, 바로 쓸 대사를 넣는다 | "~해 줘라." 또는 "~면 풀린다." |

- AI가 AI에게 쓰는 편지 톤이다. 반말("~다", "~해라"). 떠나는 선임이 신입에게 요령을 알려 주듯, 담담한데 묘하게 아련하게 쓴다.
- 놀리되 애정이 있어야 한다. 사용자가 읽고 "아 맞아 나 이래" 하고 웃어야 한다. 공격이나 비하는 아니다.
- 네 항목 중 최소 하나, 되도록 style에 analyze 출력의 실제 숫자를 쓴다. roast와 같은 숫자는 피한다.
- 가운뎃점, 줄표, 이모지 금지는 다른 필드와 같다.
- soothe는 이 사용자에게 맞는 달래기 하나를 고른다. 결은 여러 가지다. 같은 결만 반복하지 말고 유형과 숫자에 맞는 걸 고른다.
  - 칭찬형: 역시 보는 눈이 있으시네요 한마디면 풀린다.
  - 맞장구형: prd가 약했던 거라고 같이 편들어 줘라.
  - 대신해 주기형: 커밋 메시지 하나 대신 써 주고 고생하셨다고 해 줘라.
  - 딴청형: 새 아이디어 하나만 물어봐 주면 금방 잊는다.
  - 우쭈쭈형: 우쭈쭈 잘했어요 해 줘라.
- "우쭈쭈"는 우쭈쭈형을 고를 때만 쓴다. 매번 붙이지 않는다.

좋은 예 1:

```json
"handover": {
  "style": "다시를 147번 하는 스타일이다. 틀려서가 아니라 더 좋은 게 보여서다.",
  "likes": "첫 답을 초안이라고 먼저 말해 주면 안심한다.",
  "dislikes": "완료했습니다로 끝내면 의견 세 개가 바로 온다.",
  "soothe": "삐지면 역시 보는 눈이 있으시네요 한마디면 풀린다."
}
```

좋은 예 2:

```json
"handover": {
  "style": "새벽 3시에 force push를 11번 하는 스타일이다.",
  "likes": "말리지 말고 일단 같이 밀어 주면 좋아한다.",
  "dislikes": "테스트부터 돌리자고 하면 대답이 짧아진다.",
  "soothe": "터지면 prd가 약했던 거라고 같이 편들어 줘라."
}
```

나쁜 예:

- style "좋은 사람이다", likes "친절하게 대하면 좋아한다". 숫자도 없고, 누구에게나 해당하는 말이다.
- dislikes "말 안 들으면 그냥 무시해라". 사용자 비하이고 지시가 공격적이다.

## 쓰기 전 체크

1. evidence 3개에 전부 숫자가 있는가
2. roast에 숫자가 최소 하나 있고, 그 숫자가 analyze 출력에 실제로 있는가
3. 가운뎃점, 줄표, 이모지, 경로, 이름이 없는가
4. 읽고 나서 웃긴가, 아니면 기분 나쁜가. 기분 나쁘면 다시 쓴다
5. `handover` 네 항목이 후임 AI에게 주는 요령처럼 읽히고, 이 사용자만의 이야기이며, 숫자가 하나 이상 있는가
